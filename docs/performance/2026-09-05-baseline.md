# the first performance baseline

the target is 1,000 concurrent players. this report separates reaching that target from merely having a runnable load generator. a failed setup is not a successful benchmark with fewer players.

the application, generator, PostgreSQL and MinIO share a disposable GitHub runner. the artifact reports record its CPU details and database version. these are synthetic fixtures, not production accounts or replays.

the intended mixed traffic includes normal polling, public chat, spectator frames, multiplayer score frames, encrypted score submissions, website reads and replay downloads. score receipts, stored replays, object references and packet delivery are checked separately from HTTP status. the fixture maps and historical PP distribution are deliberately synthetic; they are not a scoring oracle.

## setup attempts

the first attempt stopped on a fixture foreign-key error: a local player ID had been supplied as an upstream mapper ID. the harness now leaves that upstream identity unset.

the next attempt was cancelled after roughly eight minutes of login work. its logs recorded 438 completed logins and 446 login attempts reaching the packet-building stage. it did not reach the score preflight or mixed phases. that version also failed to keep early clients polling during the ramp, so it cannot establish a simultaneous 438-player capacity result.

the corrected harness keeps established clients alive on staggered schedules, limits setup to ten minutes, and retains timing/database evidence when setup fails. a separate 100-player control uses the same database size and binary; it is not a substitute for the 1,000-player target.

## acceptance boundary

the corrected [1,000-player run](https://github.com/zigcho/zigcho/actions/runs/33940433917) reached its ten-minute setup limit with **418 logged-in players and zero recorded keepalive failures**. no mixed-traffic phase ran. the retained [measurement extract](2026-09-05-target.json) records the failure explicitly.

the runner exposed four logical CPUs on an AMD EPYC 7763 host. its seeded database was about 109 MB. this is a shared-runner measurement, not the production origin's hardware.

| setup measurement | result |
| --- | --- |
| stats/rank query executions | 89,775 |
| stats/rank query mean PostgreSQL execution | 47.95 ms |
| stats/rank query accumulated PostgreSQL execution | 4,304.42 seconds across concurrent connections |
| all instrumented PostgreSQL calls | 390,093 |
| pool-wait p99 upper bound | 250 ms |
| primary Stable session-mutex wait/hold p99 upper bound | 0.25 ms each |
| Stable poll p95/p99 upper bound during the ramp | 30 seconds |

the last row is a coarse histogram bucket bound, not an assertion that every tail request took exactly thirty seconds. incomplete requests at the cutoff are not completed latency samples. accumulated database execution is parallel work, not elapsed wall time.

the dominant query calculates both global and country rank for one player. login calls the full stats reader for each existing online player, which repeats those rank counts and also fetches grades and replay views that the Bancho stats packet does not use. that repetition is the first measured optimization target. the measured primary session mutex was short-lived; this does not establish that every other lifecycle lock is cheap.

the next change should batch the login presence/stat reads, preserve the packet values and rank tie-breaking, and rerun the exact same fixture. increasing the eight-connection pool or changing the calculator would not address the demonstrated query multiplication.

## the 100-player control

the corrected [control run](https://github.com/zigcho/zigcho/actions/runs/33941593242) completed both sixty-second phases. its [measurement extract](2026-09-05-control.json) includes all request families, resource samples and the leading database queries. its green workflow means receipt, persistence and delivery checks passed. **it is not a latency or capacity pass.**

| measurement | cold gameplay | warm |
| --- | ---: | ---: |
| completed requests | 2,001 | 2,181 |
| missed scheduled request slots | 16,903 | 16,717 |
| normal poll p95 / p99 | 6.984 s / >10 s | 6.272 s / 9.263 s |
| website read p95 / p99 | 7.563 s / 9.392 s | 6.353 s / 8.804 s |
| score p50 / p95 / p99 | all >10 s | all >10 s |
| longest score response | 29.687 s | 24.433 s |
| acknowledged / persisted / replay-backed / archived scores | 24 / 24 / 24 / 24 | 18 / 18 / 18 / 18 |
| duplicate best-score scopes | 0 | 0 |
| spectator frame deliveries | 321 | 415 |
| multiplayer score deliveries | 1,484 | 1,788 |
| chat deliveries | 9,482 | 9,990 |
| sampled server RSS peak | 156.8 MiB | 164.9 MiB |

client percentiles are one-millisecond upper bounds. `>10 s` means the quantile exceeded the client's final finite bucket, not that the measurement was missing. the score samples are small. the phase elapsed times include finishing requests already in flight: 63.52 and 65.78 seconds.

every completed request passed its response check, but the many missed slots mean the offered workload was not sustained. generator scheduling lateness stayed below four milliseconds and peak in-flight requests stayed below its own limit. all services still share a runner, so this does not isolate generator/OS interference. the short RSS samples do not prove a memory plateau or absence of leaks.

the dominant mixed-traffic query was the profile first-place listing in `src/storage/postgres/scores/stats.zig`. it ran 119 / 129 times, averaged 3.13 / 3.26 seconds, and accumulated 372 / 420 seconds of PostgreSQL execution across concurrent connections. it carried wide score/metadata rows through whole-board window sorts and wrote 560,631 / 607,864 temporary blocks. both windows returned zero first-place rows for the requested profile pages.

pool-wait p99 reached the ten-second histogram bound. PP calculation averaged about 1.7 ms for these synthetic maps. score-history snapshot queries were another substantial database cost. the first optimization should address that query work rather than increase the pool or move uploads into unbounded background tasks.

the fixture was corrected along the way for upstream mapper identity, DNS certificate verification, Stable's existing duplicate response, explicit channel joins and queued multiplayer acknowledgements. those were harness fixes, not changes to server scoring or multiplayer behaviour.
